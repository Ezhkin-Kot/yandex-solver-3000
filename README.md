# yandex-solver-3000

Автоматизация прохождения курсов на practicum.yandex.ru: раскрытие
диалоговых блоков теоретического урока, переход к следующему уроку по
готовности, автоматические ответы на квизы со случайным выбором варианта
(режим YOLO) и решение практических заданий с помощью бесплатной локальной
модели через Ollama (режим AI_SOLVE).

Управление браузером реализовано через [WebDriver](https://www.w3.org/TR/webdriver1/)
поверх `geckodriver`. Используется реальное окно Zen или Firefox с
выделенным профилем — авторизация выполняется один раз и далее сохраняется
между запусками.

## Возможности

- Раскрытие диалоговых блоков теоретического урока.
- Переход к следующему уроку по готовности.
- Ответы на квизы с выбором варианта (radio и checkbox) в режиме YOLO.
- Решение практических заданий (редактор Monaco) с помощью бесплатной
  локальной модели через Ollama, с автоматическим исправлением по тексту
  ошибки при неудачной проверке (режим `AI_SOLVE_MODE`).
- Автоматический выбор бинарника и профиля браузера в зависимости от ОС.
- Восстановление после аварийного завершения предыдущего запуска
  (зависший профиль браузера).

## Требования

- Rust (стабильный тулчейн, `cargo`).
- [`geckodriver`](https://github.com/mozilla/geckodriver) в `PATH`.
- Zen Browser или Firefox.
- [Ollama](https://ollama.com) в `PATH` — только для режима `AI_SOLVE_MODE`
  (решение практических заданий).

## Установка

### macOS

```bash
brew install geckodriver
```

Zen и Firefox предполагаются установленными стандартным образом
(`/Applications/Zen.app`, `/Applications/Firefox.app`) — путь к бинарнику
определяется автоматически.

### Linux

`geckodriver` устанавливается через пакетный менеджер дистрибутива либо
скачивается из [релизов проекта](https://github.com/mozilla/geckodriver/releases)
и помещается в `PATH`. Браузер (`zen` или `firefox`) должен быть доступен по
имени команды в `PATH` — по этому имени его находят и программа, и
`geckodriver`.

Firefox рекомендуется устанавливать через пакетный менеджер дистрибутива
(`apt`, `dnf` и т. п.), а не через snap. Snap-сборка Firefox на практике
приводит к систематическим зависаниям профиля — браузер каждый раз считает
себя "уже запущенным, но не отвечающим", предположительно из-за песочницы
snap, которая мешает `geckodriver` управлять процессом браузера. После
установки через пакетный менеджер проблема не воспроизводится.

## Сборка

```bash
cargo build --release
```

Результат сборки: `target/release/yandex-solver-3000`.

## Запуск

```bash
./target/release/yandex-solver-3000
```

При запуске открывается окно браузера с выделенным профилем бота. При
первом запуске требуется авторизация в Яндекс ID — далее профиль
сохраняется, повторная авторизация не требуется. Клики по нужным элементам
страницы урока начинаются автоматически. Остановка — по `Ctrl+C`; окно
браузера и процесс `geckodriver` закрываются автоматически.

## Конфигурация

Параметры задаются через переменные окружения либо через файл `.env` в
рабочей директории (шаблон — `.env.example`):

```bash
cp .env.example .env
```

| Переменная            | Значение по умолчанию                              | Описание                                                                   |
| --------------------- | -------------------------------------------------- | -------------------------------------------------------------------------- |
| `BROWSER`             | `zen`                                              | `zen` или `firefox`                                                        |
| `BROWSER_BINARY_PATH` | macOS: путь к `.app`; Linux: имя команды из `PATH` | Путь к бинарнику браузера                                                  |
| `BROWSER_PROFILE_DIR` | `~/.zen-bot-profile` или `~/.firefox-bot-profile`  | Директория выделенного профиля браузера                                    |
| `GECKODRIVER_PORT`    | `4445`                                             | Порт, на котором запускается `geckodriver`                                 |
| `YOLO_MODE`           | выключен                                           | `1`, `true` или `yes` — автоматические ответы на квизы случайным вариантом |
| `AI_SOLVE_MODE`       | выключен                                           | `1`, `true` или `yes` — автоматическое решение практических заданий        |
| `OLLAMA_MODEL`        | `qwen2.5-coder:3b`                                 | Модель для генерации решений                                               |
| `MAX_SOLVE_ATTEMPTS`  | `5`                                                | Число попыток исправления на одно задание перед передачей человеку         |

Значение переменной окружения имеет приоритет над значением из `.env`.

### Режим AI_SOLVE_MODE

При обнаружении страницы практического задания (редактор Monaco, кнопка
«Проверить») программа сначала нажимает «Проверить» на нетронутом стартовом
коде как есть — некоторые задания (например, финальные чекпоинты темы вида
«здесь ничего менять не нужно, просто двигайтесь дальше») уже проходят
проверку без единого изменения, и это самый надёжный способ такие задания
распознать: не по конкретной формулировке текста задания (она не гарантированно
одинаковая), а по тому же сигналу, которым пользуется сама проверка. Если эта
попытка проходит — задание засчитано, модель вообще не вызывается.

Если нет — программа читает условие задания и содержимое файлов в редакторе,
отправляет их локальной модели через Ollama (вместе с текстом ошибки из
пробной проверки, если она была), вставляет полученное решение и снова
нажимает «Проверить». Если проверка всё ещё не пройдена — текст ошибки, а
также точный предыдущий ответ модели с явной пометкой «не повторяй его»,
уходят в следующий запрос вместе с условием и текущим кодом, и так до
`MAX_SOLVE_ATTEMPTS` попыток. Если модель всё равно повторяет предыдущий ответ
дословно, для оставшихся попыток повышается температура сэмплирования — при
низкой (по умолчанию) температуре модель иначе детерминированно выдаёт один и
тот же неверный вариант независимо от того, что говорится в тексте ошибки.
При исчерпании попыток задание оставляется для решения вручную — программа не
зацикливается.

Решение вставляется через **настоящие нажатия клавиш** (клик по редактору +
выделить всё + напечатать), а не через JS API Monaco (`model.setValue()`).
Это не стилистический выбор: у этого типа заданий проверка подгружает файл
из копии, сохранённой на сервере, а такое сохранение запускается только
реальными событиями ввода — `setValue()` меняет то, что видно в редакторе,
но не доходит до сохранения, и проверка каждый раз видит старую версию
файла. Подтверждено вживую: один и тот же правильный ответ через
`setValue()` стабильно проваливал проверку, а тот же текст, напечатанный
как настоящий ввод — проходил.

Модель работает полностью локально через [Ollama](https://ollama.com) —
бесплатно, без ключей API и без отправки условий/кода куда-либо наружу.
Заранее нужно только:

```bash
brew install ollama          # если ещё не установлена
ollama pull qwen2.5-coder:3b # скачать модель (один раз)
```

Сам сервис `ollama serve` запускать не нужно — если на порту `11434` никто
не отвечает, программа поднимает его сама при старте и останавливает вместе
с браузером при выходе, точно так же, как `geckodriver`. Постоянно висящий
фоновый сервис (`brew services start ollama`) не требуется; если он всё же
включён отдельно, программа просто использует уже работающий и не трогает
его при выходе.

`qwen2.5-coder:3b` — компромиссный выбор для машин с 8 ГБ памяти: не самая
мощная модель, но оставляет памяти на браузер. На более мощной машине можно
взять модель крупнее через `OLLAMA_MODEL`.

При выключенном `AI_SOLVE_MODE` страницы практических заданий игнорируются,
как и раньше.

## Диагностика

**`binary is not a Firefox executable`**

Ошибка возвращается самим `geckodriver`. Она означает, что путь в
`BROWSER_BINARY_PATH` (или определённый по умолчанию) указывает на
обёртку или символическую ссылку, а не на исполняемый файл браузера —
`geckodriver` ищет файл метаданных приложения (`application.ini`) рядом с
указанным бинарником, а он присутствует только рядом с настоящим
исполняемым файлом внутри директории установки. На Linux часто встречается
ситуация, когда команда в `PATH` (например, `zen-browser`) является
launcher-скриптом.

Проверка типа файла:

```bash
file "$(which zen-browser)"
```

`ELF executable` означает настоящий бинарник, `shell script` — обёртку.
Поиск настоящего бинарника:

```bash
find / -maxdepth 6 -iname "application.ini" 2>/dev/null | grep -i zen
```

Путь к исполняемому файлу рядом с найденным `application.ini` указывается
в `BROWSER_BINARY_PATH`.

**`already running, but is not responding` при каждом запуске**

Разовое появление этой ошибки после аварийного завершения программы
(сбой, принудительное завершение процесса) обрабатывается автоматически:
подробности — в разделе «Восстановление после сбоя» ниже. Если ошибка
воспроизводится систематически и браузер установлен через snap — см.
раздел «Установка» выше.

## Восстановление после сбоя

Аварийное завершение предыдущего запуска (сбой, принудительное завершение
процесса, закрытие терминала) может оставить процесс браузера или файл
блокировки профиля. Программа обрабатывает эту ситуацию автоматически:

1. При неудачном подключении к браузеру выводится предупреждение с
   объяснением причины.
2. Завершается процесс, использующий директорию профиля бота
   (`SIGTERM`, поиск по аргументам командной строки — совпадение возможно
   только с процессом, запущенным именно с этим профилем; основной
   профиль браузера пользователя не затрагивается).
3. Удаляются файлы блокировки профиля (`lock`, `.parentlock`).
4. Выполняется одна повторная попытка подключения.

Ни один из этих шагов не удаляет пользовательские данные профиля (куки,
сохранённую авторизацию, историю) — удаляются только файлы блокировки.
Если повторная попытка также завершается ошибкой, программа завершает
работу с сообщением об ошибке без дальнейших автоматических действий.

## Ограничения

- Поддерживаются только уроки, построенные на диалоговых блоках
  (`theory-viewer__block_type_*`): раскрытие реплик, переход к следующему
  уроку, квизы с выбором варианта (radio и checkbox).
- При появлении незнакомого типа блока (например, задания с кодом)
  программа приостанавливает клики и ожидает ручного вмешательства; работа
  возобновляется автоматически, как только на странице снова появляется
  распознаваемый элемент.
- Режим `YOLO_MODE` отвечает на квизы случайным образом и предназначен
  только для формального прохождения урока, а не для усвоения материала.
- `AI_SOLVE_MODE` пока проверен на заданиях типа «web» (HTML/CSS/JS с живым
  превью) с файлами вида `script.js`/`index.html`. Определение языка для
  ввода кода — по расширению файла (`js` → `javascript` и т. п.); незнакомое
  расширение может не найти нужный редактор на странице.
